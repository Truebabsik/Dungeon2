## 3. Как устроено решение

**Грабли, на которые стоит посмотреть всем: `Transform3D(...)` в `.tscn` пишется ПО СТРОКАМ базиса.**
`Transform3D(0, 0, 1, 0, 4.88, 0, -6.24, ...)` — это не «колонки», а `basis.rows`: `world.x = pz`,
`world.y = 4.88·py`, `world.z = −6.24·px`. Модель `porticullus_1024.glb` в локальных координатах имеет
**ширину по X (0.641), высоту по Y (1.0246), толщину по Z (0.0647)** — то есть у решётки ширина по X
ехала в мировой z, а не наоборот. Первый прогон пробы с этой ошибкой дал «ширину 37.6 м»; поправлено.

**Расчёт новой постановки** (все числа — из AABB модели, без округления под результат):

- ширина: `0.641152 × 5.9424284 = 3.810` → мировые `z −1.905..1.905`; проём 3.8 перекрыт с запасом 5 мм
  на сторону (проверка сравнивает с `GATE_OPENING_WIDTH / 2 = 1.9` строго, ровно 3.8 легло бы на
  граничную ошибку float; 5 мм стоят ничего — в окне x = 6.95…7.03 у оболочки вообще нет граней с
  |z| < 2.0, проверено сканом по ширине до 4.04 м);
- высота и толщина не тронуты (`4.88` → верх 5.000194, толщина 0.064731 — как в T2-fix3);
- сдвиг по x: центр 6.98 = минимальное круглое значение с **реальным** зазором 0.0303 до коробки
  перемычки. Граница чистоты, посчитанная пробой: центр ≥ 6.935 (при 6.930 перекрытие с
  `ArchLintelBody` ещё 0.02087, то есть уже задет сам допуск `GATE_BOX_EPS`; при 6.935 — ноль).

**Почему не x = 6.5 и не «внутри прохода»** — см. таблицу §4. Коротко: новая лофт-полоса туннеля
занимает x 4.94…6.50 и задевает решётку на 0.04 по z; арка занимает x 6.064…6.917 и задевает её
на 0.026/0.027 по z (торцы у внутренних граней ног) и на 0.064 по y (верх 5.0 против низа коробки
перемычки 4.936). Между ними окна нет: перекрытие считается по объёму (`GATE_BOX_EPS = 0.02` по всем
трём осям сразу), а требуемое перекрытие проёма по z (±1.9) заведомо больше 0.02.

**Почему именно «перед фасадом», а не «внутри купола»: подъём.** Решётка 5.0 м обязана целиком уйти вверх
(ledger, п. 6). Над проёмом в плоскости x = 6.947…7.012 **граней оболочки выше y = 5 нет вообще**
(`НАД_ПРОЁМОМ три=0`), а коробки арки в этой полосе по x не стоят. То есть поднятая решётка не клипает
ни лофт-полосу туннеля (потолок прохода на x < 6.5 — это как раз тот самый блокер), ни перемычку арки.
Любая постановка внутри прохода (x ≤ 6.51) упирается в потолок туннеля на y = 5.0 и подъём невозможен.

## 5. Решения вопреки брифу

1. **Отправная точка (b) — плоскость проёма x = 6.5 — отвергнута замерами, а не вкусом.** С новой
   геометрией (лофт-полоса) и тремя коробками арки в плоскости x = 6.5 красны все три: 2 треугольника
   полосы + три коробки. Уточнение коробки перемычки (которое бриф разрешал) сняло бы только y-перекрытие
   0.0643, но **торцы решётки всё равно заходят в коробки ног на 0.026/0.027** — их бриф править не
   разрешал, а сузить решётку до 3.747 нельзя: `check_gate_portcullis` требует перекрытия ±1.9. Поэтому
   разрешённое уточнение **не понадобилось и не сделано**: `game/tests/level_check.gd` не изменён ни
   на строку, все пороги и допуски прежние.
2. **Решётка вынесена из плоскости ворот в рот двора (центр x = 6.98).** Обоснование в §3/§4: это
   единственная измеренно чистая постановка и единственная, где подъём физически возможен. Побочный
   эффект, который видит игрок: решётка висит перед камнем арки и перед фасадом (зазор 3–5 см), а не
   внутри откоса проёма. Это решение ведущего — см. §8.
3. **Ширина 3.81, а не ровно 3.8** — 5 мм запаса на сторону против граничного сравнения во float.
   Порог не тронут, запас добавлен в геометрию, а не в проверку.

## 8. Что заметил и не стал делать

- **Решётка вне плоскости ворот — вопрос к ведущему, а не решённый мной факт.** Если нужен вид
  «решётка внутри откоса проёма», чистых вариантов нет: (а) сдвинуть коробки ног наружу на 0.027 —
  это правка `check_gate_arch` сверх разрешённого (уточнение разрешено только для перемычки) и
  сужение просвета коллизий с 3.75 до 3.80; (б) прорезать в лофт-полосе туннеля паз под решётку —
  это `build_cave_gate.py`, вне области и с пересборкой glb; (в) сдвинуть арку по x — ломает
  `ARCH_CUT_X` и прилегание к куполу (fix3 §5.2). Оставил как есть, решение за ведущим.
- **Лофт-полоса туннеля стоит поперёк пути подъёма.** При любой постановке x < 6.52 поднятая решётка
  упрётся в её потолок y = 5.0. Это ограничение на будущую задачу 3 (`open_height`): ход решётки
  должен быть вертикальным в полосе x ≈ 6.95…7.01, где сверху пусто.
- **Замер `PASS` на плоскости самой решётки (x = 6.98) даёт «нет потолка» и неограниченную ширину** —
  это правильно (плоскость стоит во дворе, вне купола), но означает, что проход там не измеряется;
  проход мерялся в x = 6.3/6.5/6.7.
- **В пробе ширина/высота считались по AABB треугольников** — той же логикой, что и проверка. Для
  «свободного прохода» это консервативно (AABB грани толще самой грани), но зато совпадает с контрактом.
- **`NEAREST_Z = inf` в окне решётки** — не ошибка пробы, а факт: в полосе x 6.95…7.03, y 0…5 граней
  оболочки нет вообще (купол у |z| = 1.9 кончается на x = 6.946, дальше двор).
- **Первый прогон пробы был неверным из-за трактовки `Transform3D` в `.tscn` как матрицы по колонкам**
  (см. §3). Поймано сравнением с AABB узла: `portc.transform * model` против `prop_world_aabb(Portcullis)`
  дали `равно=true` только после исправления осей. Стоит держать в голове при правках любых
  трансформов в сценах этого проекта.
- **`Minecart`** — вне области (задача 6).
- **Временные файлы в `E:\Temp\opencode\`:** `fix5b_gate_backup.tscn` (сцена до правок),
  `fix5b_gate_after.tscn` (рабочая, эталон для откатов), `fix5b_faces.txt` (дамп граней),
  `fix5b_probe*.log` (пробы), `fix5b_mut_a.log`, `fix5b_mut_b.log`, `fix5b_gate1.log`,
