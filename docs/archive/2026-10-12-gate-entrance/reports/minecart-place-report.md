## Позиция и обоснование

**`Minecart` = (67.3, 2.05, 33.0).**

Обследовал 9 кандидатов вокруг старта персонажа (66, 2.05, 34) по данным сцены: верх пола в точке,
ближайшая стена, расстояние до коллизии капсулы персонажа, боковой зазор коридора движения
старт → -Z. Победитель:

- пол под центром ровно `y = 2.05` — низ коллизии совпадает с полом без подрезки;
- пересечений со стенами нет, ближайшая `Wall_17_0_8` на **1.444 м**;
- расстояние до коллизии персонажа **1.1143 м** > 0.35 (капсула не задевает);
- боковой зазор коридора движения **0.504 м** — максимум среди кандидатов с нормальным полом;
- вагонетка справа-впереди старта, в поле зрения от первого лица, не перекрывает выход из старта.

## Коллизия: выбор

**`BoxShape3D` по AABB меша**, `size = (0.885818, 0.953226, 0.566331)`, смещение
`CollisionShape3D = (-0.003415, 0.476613, 0.000664)` (низ коробки на уровне пола).

Почему box, а не trimesh: вагонетка близка к коробке (AABB меша 0.89 × 0.95 × 0.57 м, 11 804 треуг.
не окупают trimesh-коллизию для статичного декора), бриф прямо предлагает box по AABB, и дешёвая
box-коллизия лучше для физики капсулы. Грубость box проверена геометрически: AABB меша в мировых
координатах совпадает с AABB коллизии с точностью до микрон (см. вывод пробы), то есть лишних
«мёртвых» зон нет — коробка опирается ровно на габарит меша.

## Структура узла (и почему не «голый» MeshInstance3D)

Реализован вариант по брифу:

```
Minecart (Node3D) @ (67.3, 2.05, 33.0)
├── minecart  — инстанс res://assets/minecart.glb (корень glb → node_0:MeshInstance3D)
└── StaticBody3D
    └── CollisionShape3D (BoxShape3D)
```

Пробовал вариант «MeshInstance3D напрямую с мешем-ресурсом из glb» (чтобы не тащить лишний узел).
В Godot 4.7 это **недостижимо**: `ext_resource` с путём-субресурсом `res://assets/minecart.glb::ArrayMesh_lgoh3`
отклоняется парсером сцены (`Parse Error: [ext_resource] referenced non-existent resource`), а
`ResourceLoader.load(..., CACHE_MODE_IGNORE)` на таком пути тоже FAIL (дословно в выводе пробы ниже:
`ERROR: Resource file not found: res://assets/minecart.glb::ArrayMesh_lgoh3 (expected type: ArrayMesh)`).
Ранее ложно-положительный `exists()` был следом кэша. Единственный рабочий путь — инстансировать
glb-сцены целиком, т.е. структура выше.

Все остальные проверки — `ok`; единственная причина `failed: 1` — строка
`ПРОВАЛ модули без инстанса .gltf: Minecart`.

### Причина падения (дефект вне области задачи)

`collect_modules` в `game/tests/level_check.gd` трактует **любого прямого `Node3D`-потомка корня
Level** как «модуль» и требует, чтобы у него был инстанс из `.gltf` (`.glb` тоже не принимается —
сравнение, судя по сообщению, по расширению `.gltf`). Новый узел `Minecart (Node3D)` — не инстанс
gltf-модуля, поэтому проверка падает. Это не дефект постановки вагонетки, а жёсткая эвристика
проверки, которая не различает «декоративный узел» и «модуль». Проверку по брифу **не правил**.
